# VPSPC 主控与被控端一键更新、彻底卸载设计

日期：2026-08-27  
状态：已完成交互设计确认，等待实施前复核

## 1. 目标

为 VPSPC 增加统一的更新与彻底卸载能力，并同时提供 Telegram Bot 和 Web 管理入口。

更新范围包括：

- 仅更新主控。
- 更新指定在线被控端或全部在线被控端。
- 先更新主控，再更新全部在线被控端。
- 选择最新稳定版、最新测试版或指定 Release。
- 支持原生 systemd 主控和 Docker Compose 主控。
- 被控端继续使用原生 systemd 轻量探针，不提供 Docker 版。

卸载范围包括：

- 彻底卸载指定在线被控端或全部在线被控端。
- 先彻底卸载全部在线被控端，全部成功后再彻底卸载主控。
- 删除 VPSPC 自己创建的程序、服务、配置、密钥、状态、缓存、数据库和日志。
- 严格保留所有非 VPSPC 资源。

## 2. 不在本次范围内

- 不允许主控通过 SSH 登录被控端。
- 不给被控端开放监听端口。
- 不保存 SSH 密钥或其他服务器登录凭据。
- 不支持被控端 Docker 部署。
- 不支持自动安装更新。
- 不接受任意下载 URL、Git 分支、提交哈希或 Shell 命令。
- 不保留更新和卸载历史记录。
- 不清理系统共享 journald 历史库。
- 不修改或删除 Xray、sing-box、V2Board、妙妙屋 X、`xrayagent` 等第三方服务、配置、数据库或日志。

## 3. 总体架构

### 3.1 版本检查器

主控每天检查一次：

- 最新稳定版 GitHub Release。
- 最新测试版 `main` 发布产物。
- 可用于指定版本的已发布 Release 列表。

版本检查只缓存版本号、发布时间、提交标识、兼容范围和校验信息，不安装更新，也不发送 Telegram 通知。设置中可以关闭每日检查。管理员手动点击检查时，必须忽略缓存并立即重新检查。

无更新时 TG/Web 按钮显示“检查更新”；检测到稳定版或测试版有新产物时显示“检测到可用更新”。这里的更新会短暂重启相关服务，不使用“热更新”表述。

### 3.2 升级协调器

Telegram 和 Web 共用同一个协调器和任务状态机。协调器负责：

- 校验管理员权限和确认码。
- 获取允许安装的版本清单。
- 判断主控部署方式。
- 判断被控端在线状态。
- 建立短期任务和并发批次。
- 汇总成功、失败、回滚、过期和跳过结果。
- 保证同一时间只执行一个升级或卸载任务。

任务状态为：

`created → claimed → downloading → installing → verifying → success`

异常终态包括：

- `rolled_back`
- `failed`
- `expired`
- `cancelled`
- `safely_retained`

任务尚未被领取时允许取消；进入替换或删除阶段后不允许强行中断。

### 3.3 主控更新助手

主控安装一个 root 所有、权限受限的宿主机更新助手。它只接受固定结构的升级、回滚和彻底卸载请求，不接受调用方传入的 Shell、任意路径、任意 URL 或 Docker 参数。

原生部署由助手完成程序原子切换、systemd 重启和健康检查。Docker 部署由助手在宿主机更新 Compose 镜像 digest。Web/Bot 容器不挂载 Docker Socket。

主控更新由独立助手接管，因此 Web 和 Bot 在升级中重启不会中断任务。服务恢复后读取当前任务的临时结果并展示。

### 3.4 被控端命令心跳

被控端增加独立的轻量命令心跳：

- 每 60 秒通过现有 HTTPS/HMAC 信任链主动联系主控。
- 最近 120 秒内有成功心跳才视为在线。
- 升级或卸载任务必须在创建后 120 秒内被领取。
- 超时任务失效，不在节点以后上线时补执行。
- 日志和审计数据仍使用现有上报周期。

节点领取任务后可以在任务有效期外完成已经开始的升级或清理，但必须持续上报阶段状态。节点在领取前再次验证任务 ID、目标节点、时间、nonce 和 HMAC。

### 3.5 GitHub 发布流水线

GitHub Actions 在完整测试通过后发布：

- Release 稳定版原生更新包、节点探针、版本清单和 SHA-256。
- `main` 测试版原生更新包、节点探针、提交标识、版本清单和 SHA-256。
- 带固定版本、提交标签和 digest 的 GHCR Docker 镜像。

最新稳定版来自正式 Release；测试版来自最新 `main` 产物；指定版本只列出已发布 Release。指定版本可以用于升级或降级，但兼容检查不通过时必须拒绝执行。

主控先下载并校验节点产物，再通过现有 HTTPS 节点接收域名提供固定产物；被控端不需要直接访问 GitHub。任务中包含预期版本和 SHA-256，节点下载后再次校验。

## 4. 更新流程

### 4.1 目标选择

提供三个更新入口：

1. 仅升级主控。
2. 升级被控端，随后选择指定在线节点或全部在线节点。
3. 升级主控和全部在线被控端。

版本选择提供：

- 稳定版：最新正式 Release。
- 测试版：最新 `main` 产物。
- 指定版本：从 Release 列表分页选择。

确认页显示当前版本、目标版本、部署方式、目标节点和服务短暂重启提示。已经处于相同版本的目标自动跳过。

### 4.2 主控原生更新

1. 从固定 GitHub 仓库获取目标清单和更新包。
2. 验证仓库、Release 或提交标识、兼容范围和 SHA-256。
3. 安全解压到 VPSPC 临时目录，拒绝绝对路径、`..`、链接逃逸和超限文件。
4. 执行 Python 编译、配置读取和基础自检。
5. 暂存当前程序作为本次操作的回滚副本。
6. 原子切换新程序。
7. 重启巡查器、节点接收端、Telegram Bot 和 Web。
8. 检查 systemd 状态、Web 健康接口和节点接收接口。
9. 成功后立即删除旧程序副本、下载包和临时目录。
10. 失败时恢复旧程序，重启并确认恢复成功，再清理临时文件。

更新包不得覆盖配置、Token、节点密钥、审计数据或第三方日志。

### 4.3 Docker 主控更新

1. 更新助手保存当前 VPSPC 镜像 digest 和 Compose 目标。
2. 拉取指定的不可变目标 digest。
3. 只更新 VPSPC Compose 服务。
4. 启动并检查容器健康状态及 Web/节点接收接口。
5. 成功后删除已不再使用的上一版 VPSPC 镜像。
6. 失败时恢复原 digest 并重新启动。

不得执行全局 `docker system prune`，不得修改或删除其他 Compose 项目、容器、镜像、网络或卷。

### 4.4 被控端更新

1. 在线节点通过 60 秒心跳领取短期任务。
2. 节点验证任务归属、有效期、版本和兼容范围。
3. 将探针下载到 VPSPC 自己的临时目录并校验 SHA-256。
4. 执行 Python 编译检查。
5. 一次性更新助手备份当前探针并原子替换。
6. 重启探针，完成主控认证和命令心跳健康检查。
7. 成功后上报结果并删除旧探针、下载包和临时文件。
8. 失败时恢复旧探针、重启、上报“失败且已回滚”，然后清理临时文件。

被控端更新只能修改 VPSPC 自己的安装、配置、状态和 systemd unit，不扫描、修改或重启任何节点服务。

### 4.5 主控和全部被控端更新

1. 先升级主控并完成健康检查。
2. 主控失败时自动回滚，不启动节点升级。
3. 主控成功后，记录当时在线的被控端目标集合。
4. 默认每批并发 3 台，可配置为 1 至 10 台。
5. 某台失败时只回滚该节点，后续批次继续。
6. 全部执行完成后汇总成功、失败、回滚和跳过结果。

离线节点直接跳过，不建立待执行任务。失败节点不自动重试，并保持升级前版本。已成功节点不因其他节点失败而降级。

### 4.6 兼容策略

每个发布清单声明：

- 主控协议版本。
- 被控端协议版本。
- 支持的配置格式范围。
- 最低可升级和降级版本。

更新助手在写入任何生产文件前完成兼容预检。配置迁移必须可在本次健康检查失败时回滚。目标版本不能安全读取当前配置时，指定版本操作必须被拒绝，不能强制覆盖配置。

## 5. Telegram 交互

主菜单新增：

- `🔄 更新管理`
- `🧹 彻底卸载`

更新管理页显示主控当前版本、部署方式、最新稳定版、最新测试版、在线节点数量和每日检查状态，并提供：

- `检查更新` 或 `检测到可用更新`
- `仅升级主控`
- `升级被控端`
- `升级主控＋全部在线被控端`
- `开启/关闭每日版本检查`

指定节点使用 Telegram 节点按钮勾选，选中后显示 `✅ 被控端名称`，再点击“完成选择”。指定 Release 使用分页按钮选择，不要求手动输入版本号。

执行期间尽量编辑同一条 Telegram 消息显示进度，例如“已完成 6/10，成功 5，失败 1”。完成后显示失败节点名称、原版本、目标版本和必要错误摘要。

彻底卸载页提供：

- `彻底卸载被控端`
- `彻底卸载主控＋被控端`

被控端卸载支持指定在线节点或全部在线节点。确认页必须明确列出删除范围和第三方保留范围。

## 6. Web 交互

Web 管理台增加“更新管理”和“彻底卸载”页面。更新页包含：

- 主控版本、部署方式、稳定版和测试版状态。
- 被控端名称、版本、最后心跳和在线状态。
- 指定节点复选框和“选择全部在线节点”。
- 稳定版、测试版和指定 Release 选择。
- 当前任务进度和结果。

卸载页使用与 Telegram 相同的范围说明、动态确认码和任务锁。危险按钮必须与普通操作视觉区分。

全套卸载最终启动后，Web 显示主控即将停止；随后页面无法访问属于预期结果。

## 7. 确认与权限

- Telegram 必须同时匹配已配置的管理员 Chat ID 和用户 ID。
- Web 必须使用 Web Token。
- 升级必须显示目标和版本并人工确认。
- 彻底卸载先显示精确删除范围，再要求动态 6 位确认码。
- 确认码只保存哈希，5 分钟失效且只能使用一次。
- 主控和被控端全套卸载在所有在线被控端成功后，还必须进行最终“确认彻底删除主控”。
- 同一时间只允许一个升级或卸载任务；TG 和 Web 共享任务锁。

## 8. 彻底卸载与资源归属

### 8.1 归属模型

安装器维护 VPSPC 归属清单，并为受管目录写入管理标记。删除必须同时满足：

1. 资源存在于 VPSPC 归属清单。
2. 文件或目录管理标记匹配。
3. 目标是经过验证的具体安全路径。
4. 资源没有被识别为第三方或共享用途。

任何一项不满足时都必须拒绝删除并报告“已安全保留”。不得使用根目录、用户主目录、未解析变量、宽泛通配符或未验证路径作为递归删除目标。

### 8.2 被控端彻底卸载

删除：

- VPSPC 探针程序、命令入口和一次性助手。
- VPSPC systemd 服务、定时器和命令心跳。
- 节点配置、密钥、状态、缓存和待上报队列。
- VPSPC 自身日志、更新包、临时文件和回滚文件。
- VPSPC 管理标记和清理后的空受管目录。

绝不删除或修改：

- Xray、sing-box、V2Board、妙妙屋 X。
- `xrayagent` 等向其他主控汇报的节点服务。
- 第三方 systemd 服务、数据库、配置和日志。
- VPSPC 只读采集的原始日志路径。

删除前先完成完整预检。预检失败时不开始删除。

### 8.3 被控端最终回执

1. 节点收到命令后先做归属和路径预检。
2. 预检通过后启动一次性清理助手。
3. 助手删除 VPSPC 内容。
4. 助手使用只对当前任务有效的两分钟一次性凭据报告最终结果。
5. 回执凭据不能上报审计数据或领取其他命令。
6. 回执完成后，助手和凭据自删除。

主控只有收到最终成功回执才将节点标记为彻底卸载。回执丢失或节点掉线按失败处理，主控在全套卸载中必须保留。

### 8.4 主控原生彻底卸载

删除 VPSPC 自己拥有的：

- 巡查、Web、Bot、节点接收和更新助手服务。
- 程序、虚拟环境、受管源码和命令入口。
- 配置、Web Token、Telegram/AI 配置、节点注册表和节点凭据。
- 状态、报告、事件、连接归档、缓存、临时任务、备份和自身日志。
- 自动下载的 GeoLite2 City/ASN 数据库。
- systemd unit 和管理标记。

Falco 处理规则：

- 安装 VPSPC 前已经存在时，保留 Falco，只删除 VPSPC 规则和输出。
- 由 VPSPC 独占安装且没有被其他用途修改时，可以删除 VPSPC 安装的 Falco。
- 发现外部修改或共享用途时，保留 Falco，只删除能明确确认属于 VPSPC 的内容。

### 8.5 Docker 主控彻底卸载

只删除归属 VPSPC Compose 项目的容器、专用网络、专用卷、镜像、Compose 文件、带管理标记的挂载目录和宿主机更新助手。

不得卸载 Docker，不得执行全局清理，不得删除其他项目资源，也不得删除没有 VPSPC 标签和归属记录的 Docker 资源。

### 8.6 全套卸载顺序

1. 记录当前 120 秒内在线的被控端目标集合。
2. 展示范围并第一次确认。
3. 验证 5 分钟有效的一次性 6 位确认码。
4. 默认并发 3，彻底清理全部目标节点。
5. 任意节点失败、掉线或缺少最终回执时，保留主控并显示失败节点。
6. 全部节点成功后，显示最终主控删除确认。
7. Telegram 在删除前发送最终状态；Web 显示即将离线。
8. 独立清理助手删除主控并最后删除自己。

离线节点不处理、不排队，也不在以后上线时补执行。

## 9. 日志与临时状态

不建立更新和卸载历史记录。只保存当前任务正常执行和跨服务重启所需的临时状态：

- Telegram 成功展示最终结果后立即删除。
- Web 成功读取最终结果后立即删除。
- 未查看结果最多保留 24 小时。
- 不保存 Token、节点密钥、确认码、敏感下载参数或完整命令。
- 彻底卸载时无条件删除。

VPSPC 自己管理的日志文件全部属于彻底卸载范围。共享 journald 中可能存在少量历史服务记录；不得为删除这些记录而清空或轮转整个系统日志库。

## 10. 错误与结果展示

错误按阶段归类：

- 下载失败。
- 校验失败。
- 版本或协议不兼容。
- 磁盘空间不足。
- 安装前检查失败。
- 服务重启或健康检查失败。
- 升级失败且已回滚。
- 回滚失败。
- 节点离线、任务过期或回执超时。
- 归属检查失败，资源已安全保留。

显示内容只包含必要摘要，不得包含 Token、密钥、确认码或完整敏感命令。

批量升级完成后必须显示每个失败节点的被控端名称、原版本、目标版本和错误阶段。批量升级中的单节点失败不停止后续批次。

全套卸载中的任意失败必须中止主控卸载，并保留重试所需的管理能力。

## 11. 测试策略

自动测试覆盖：

- 稳定版、测试版和指定 Release 解析。
- 发布清单、SHA-256 和镜像 digest 校验。
- 在线状态、心跳超时、任务领取、取消、过期和重放拒绝。
- 指定节点、全部在线节点和并发批次。
- 原生主控更新、健康检查和自动回滚。
- Docker 主控更新、健康检查和自动回滚。
- 被控端更新、回滚和结果汇总。
- Telegram 节点按钮和 Web 复选框选择。
- 动态确认码失效、一次性使用和越权拒绝。
- 非法版本、非法 URL、非法路径和归档路径穿越拒绝。
- GeoLite2 等 VPSPC 归属数据清理。
- 第三方服务、配置、数据库和日志保留。
- 妙妙屋 X、Xray、`xrayagent` 等测试哨兵在彻底卸载后仍完整存在。
- 全套卸载部分失败时主控必须保留。
- 临时状态查看后删除和 24 小时过期。
- 不生成操作历史记录。

破坏性测试只能在临时目录、测试容器或专用测试虚拟机中运行，不得在现有 Oracle 或生产节点上试删。

## 12. 验收标准

- TG 和 Web 均可完成主控、指定被控、全部在线被控和整套环境更新。
- 支持最新稳定版、最新测试版和指定 Release。
- 原生与 Docker 主控均能更新并在失败时自动回滚。
- 被控端无需开放端口，命令心跳开销轻量。
- 离线节点不排队、不补执行。
- 批量更新中的节点失败不阻塞后续批次，并能准确列出失败节点。
- 更新成功后不遗留下载包和回滚副本。
